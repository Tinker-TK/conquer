# 遗物流派设计：60 件与战斗联动的遗物

> 面向当前 Godot 项目（能量 / 抽牌 / 征召 / 自动交锋 / 回合结算）的遗物扩展方案。
> 目标不是「再加几个 +攻 +血」，而是让每件遗物都改变一次战斗决策，让 3–5 件同流派遗物叠出可识别的玩法。
> 配置方式见 [遗物与药水配置说明](遗物与药水配置说明.md)；本文只谈设计与落地切口。

---

## 0. 一页结论

- 当前可用遗物 **6 件**，全部是静态数值或单一资源，**没有触发器**，无法响应战斗里发生的事；普通战斗 5%、Boss 10% 的掉率意味着一局常常 0–1 件。
- 建议把遗物从「5 种固定 Kind」升级为「**触发器 + 效果处理器**」：先加 `trigger`、`rarity`、`tags`、触发次数上限四个字段，再按流派填内容。
- 60 件新遗物按 **8 条战斗流派 + 经济 + 中立** 组织；大体配比：**1 引擎 + 2 放大 + 2 补丁 + 1 终结**，保证「拿到 2–3 件就感觉在玩另一个流派」。
- 配套改掉率：普通战斗 10–12%、Boss 100%、宝箱三选一、商店按稀有度分层；一局预期 **8–10 件**。
- 先做 **12 件**（见 9.3）就能验证主要触发类型，再批量填表；旧 6 件效果不动。

## 1. 现状核对

### 1.1 数值基线

设计遗物前先把「一单位资源值多少钱」钉死，否则数值会飘。

| 项目 | 当前值 | 出处 |
| --- | --- | --- |
| 玩家初始生命 / 上限 | 80 / 80 | `data/run/run_start_data.gd` |
| 初始金币 | 99 | 同上 |
| 每场战斗敌方 HP 池 | 45（默认） | `data/levels/battle_level_config.gd` |
| 能量 | 首轮 3，每轮 +1，基础封顶 10；遗物附加能量不受封顶 | 同上 |
| 每轮抽牌 | 5 | `scripts/cards/hand_manager.gd` |
| 回合结算扣血 | 当前轮数 + 获胜方每个存活单位的 `hp_damage_value` | `scripts/battle/battle_round_manager.gd` |
| 单位攻击 / 生命 | 约 10–20 / 50–100 | `data/units/*.tres` |
| 单卡费用 | 0–3 | `data/cards/*.tres` |
| 阵亡或清场回弃牌堆 | 原征召牌 **+1 费**（不灭军势时 +2） | `scripts/cards/card_battle_runtime.gd` |
| 中毒 | 按层数，每回合结束每层 1 点无视防御，持续本场 | `scripts/cards/card_battle_runtime.gd` |
| 流血 | 每秒固定伤害，无视防御 | `scripts/units/unit_status_runtime.gd` |
| 护盾 | 只在交锋阶段存在，准备阶段清空 | `scripts/units/unit_base.gd` |

**换算尺**（用于估强度）：

- 1 点能量 ≈ 1 张 1 费牌 ≈ 普通遗物一次触发。
- 1 张抽牌 ≈ 0.4 点能量（考虑手牌溢出的浪费）。
- 全体 +1 攻 ≈ 单体 +5 攻（按 4–5 人场估）。
- 5 点真实伤害 ≈ 一次普通命中（无视防御，价值更高）。
- 1 点能量 ≈ 1.3 点生命（「血契补给」4 血换 3 能量，即 1 血 ≈ 0.75 能量）。

### 1.2 当前遗物

| 遗物 | 机制 | 实际效果 | 问题 |
| --- | --- | --- | --- |
| 十抽引擎 `draw_engine` | DRAW_ENERGY | 每实际抽 10 张，本回合 +1 能量 | 唯一有「进度感」的遗物，但只服务抽牌 |
| 行军戒指 `draw_ring` | DRAW_ENERGY | 每实际抽 8 张，本回合 +1 能量 | 与上面同质，纯数值差 |
| 坚城之心 `base_heart` | BASE_HEALTH | 生命上限 +20 | 纯数值 |
| 旅人护符 `traveler_amulet` | BASE_HEALTH | 生命上限 +12 | 纯数值 |
| 储能水晶 `reserve_crystal` | MAX_ENERGY | 每回合最大能量 +1 | 纯数值，且是最强的一档 |
| 出征护甲 `opening_armour` | OPENING_DEFENCE | 开战 3 轮内己方**士兵**防御 +2 | 只认士兵，覆盖面极窄 |
| 旧城防 `base_armour` | BASE_DEFENCE | 已停用 | 会被奖励池过滤 |

### 1.3 为什么现在形不成流派

1. **没有触发器**：遗物只在「获得时」和「抽牌时」生效，战斗中的部署、死亡、击杀、受击、治疗、回合结算全部接不上。
2. **没有稀有度与标签**：掉落池是一锅端，玩家无法通过选择把遗物往一个方向堆。
3. **数量太少**：6 件里还有 2 件同质（抽牌引擎 / 行军戒指）、2 件同质（生命上限）。真正可选的搭配不超过 4 种。
4. **掉率太低**：按每局约 15 场战斗算，5%/10% 的期望只有 1–2 件，连「凑一套」的机会都没有。
5. **效果不可见**：自动交锋里，玩家很难感知「+2 防御」到底生效没有，更谈不上围绕它做决策。

## 2. 设计原则

### 2.1 六条硬规则

1. **每件遗物至少连接两个系统**：能量 / 手牌 / 单位 / 状态 / 回合 / 经济，任选其二。只加一个数字的遗物不收。
2. **每件遗物必须改变一次决策**：拿牌顺序、部署位置、是否送死、是否留手牌、先打谁。改不了决策的遗物只能当填充。
3. **触发必须可见**：HUD 提示 + 战斗跳字，否则自动战斗里等于不存在。
4. **默认每场重置**：只有明确写「本局」的计数才跨战斗，并且要进存档键。
5. **同类百分比走加法池并设上限**：禁止「+20% 再 ×1.2 再 ×1.15」的乘算链。
6. **不制造无限循环**：抽牌→能量→抽牌、死亡→回手→死亡、治疗→护盾→治疗，必须带每回合/每场上限。

### 2.2 一件遗物在流派里的四种角色

| 角色 | 作用 | 例子 | 占比 |
| --- | --- | --- | --- |
| **引擎** | 改变资源流向，让流派转起来 | 军团旗幡、腐蚀之瓶、魔术手套 | 约 25% |
| **放大** | 把已有资源换成更高收益 | 疫医面具、淬火铁砧、传承之证 | 约 35% |
| **补丁** | 补流派的短板 | 阵亡抚恤、独狼徽记、背水一战 | 约 25% |
| **终结** | 首领级，给流派一个明确的终点 | 大地祭坛、王者之剑、焚城之焰 | 约 15% |

每个流派大体按「1 引擎 + 2 放大 + 2 补丁 + 1 终结」配，允许 5–8 件的浮动；拿到任意 3 件就能感到方向，拿到 5 件开始质变。

### 2.3 强度预算

| 稀有度 | 预算 | 参考 |
| --- | --- | --- |
| 普通 | ≈ 0.7 张 1 费牌 | 一次 +2 攻 / +5 生命 / 5 点真伤 |
| 稀有 | ≈ 1.5 张 1 费牌 | 每轮 +1 能量（有条件）/ 全队 +2 防 / 一次复活 |
| 首领 | ≈ 改变一条规则 | 每场免死一次 / 每轮白嫖伤害 / 遗物掉率提升 |

对照现有最强遗物「储能水晶」：它给每回合 +1 上限能量，属于稀有偏上。**新的普通遗物不应稳定超过它的一半收益**。

### 2.4 流派互斥

互斥不是 bug，是让选择有意义：

| 流派 A | 流派 B | 冲突点 |
| --- | --- | --- |
| 军团铺场 | 单核养成 | 场上人数：铺场要 ≥4，单核要 =1 |
| 亡语献祭 | 防守续航 | 是否希望单位死 |
| 毒火持续 | 单核爆发 | 需要时间 vs 需要速杀 |
| 循环连招 | 高费单核 | 低费多牌 vs 少牌高费 |
| 远程风筝 | 近战铺场 | 站位与距离收益 |

## 3. 触发器规范

### 3.1 触发时机表

这是整个扩展的地基。**先把这张表定死，再写遗物**，否则 60 件遗物会出现 60 种结算顺序。

| Trigger | 触发点 | 频率 | 典型遗物 |
| --- | --- | --- | --- |
| `BATTLE_START` | 进入战斗、首轮抽牌前 | 每场 1 次 | 战术沙盘、命运硬币 |
| `ROUND_START` | 每轮准备阶段、抽牌前 | 每轮 1 次 | 军团旗幡、恐惧图腾 |
| `SHUFFLE` | 抽牌堆抽空、弃牌堆洗回 | 每次 | 备用箭袋 |
| `CARD_PLAYED` | 卡牌成功结算后 | 每次 | 淬火铁砧、魔术手套、永动齿轮 |
| `UNIT_DEPLOYED` | 征召牌成功部署 | 每次 | 征兵名册、集结烽火、决斗契约 |
| `UNIT_DIED` | 任意正式单位死亡（清场不算，payload 带阵营） | 每次 | 骨灰之瓮、送葬人、死亡回响、焚城之焰 |
| `UNIT_KILL` | 己方单位击杀敌人 | 每次 | 血契之石、王者之剑 |
| `UNIT_HIT` | 己方单位攻击命中 | 每次 | 腐蚀之瓶、猎手标记 |
| `UNIT_HURT` | 己方单位受到攻击 | 每次 | 荆棘之甲 |
| `UNIT_HEALED` | 己方单位被治疗 | 每次 | 血库 |
| `DOT_TICK` | 中毒 / 流血每次结算后 | 每次 | 慢性死亡 |
| `COUNTER` | 己方单位触发防守反击 | 每次 | 反击姿态 |
| `ROUND_END` | 交锋结束、结算伤害前 | 每轮 1 次 | 圣徽之戒、沉稳之手、借来的时间 |
| `ROUND_SETTLED` | 回合伤害结算完成 | 每轮 1 次 | 大地祭坛、不落堡垒 |
| `BATTLE_WON` | 战斗胜利、发奖前 | 每场 1 次 | 旅者钱袋、贪婪之杯、战地急救 |
| `SHOP_OPEN` | 商店议价 | 每次 | 商人印记 |
| `RELIC_GAINED` | 获得任意遗物 | 每次 | 遗物猎人 |

> 预留但暂未使用：`RUN_START`、`AFTER_DRAW`、`CARD_DISCARDED`、`POTION_USED`。先在枚举里占位，等有对应遗物再接，避免以后改编号。
>
> 约定：`UNIT_DIED` **不包含**回合结束清场（`clear_round_units`），也不包含「撤回」；只有 `die()` 才算。

### 3.2 结算顺序

同一时机内，固定按以下顺序执行，避免顺序不同导致结果不同：

1. 玩家资源类（生命、金币、能量上限）
2. 单位属性类（攻、防、生命上限、冷却）
3. 状态类（毒、流血、虚弱、易伤、眩晕）
4. 伤害/治疗类（真实伤害、回复、护盾）
5. 抽牌/弃牌类

同一遗物有多条效果时，按 `effects` 数组顺序执行。**遗物之间不递归触发**：A 的伤害杀死单位，不再触发 B 的「死亡时」效果，除非该效果明确写「可连锁」。

### 3.3 频率与上限

每件遗物必须声明三个上限，默认值写在资源里：

```gdscript
@export_range(0, 99, 1) var max_per_battle: int = 0   # 0 = 不限
@export_range(0, 99, 1) var max_per_round: int = 0
@export_range(0.0, 10.0, 0.05) var cooldown_seconds: float = 0.0
```

| 写法 | 含义 |
| --- | --- |
| `max_per_battle = 1` | 每场一次（复活、全控） |
| `max_per_round = 1` | 每回合一次（击杀回血、死亡抽牌） |
| `cooldown_seconds = 1.0` | 同一敌人每秒最多触发一次（荆棘、附毒） |
| `0` | 不限，但只用于低强度效果 |

### 3.4 数据结构建议

保留 `kind` 兼容旧 6 件，新增字段只服务新遗物：

```gdscript
# data/relics/relic_definition.gd
enum Kind { DRAW_ENERGY, BASE_HEALTH, BASE_DEFENCE, OPENING_DEFENCE, MAX_ENERGY, NONE }
enum Trigger {
	NONE, RUN_START, BATTLE_START, ROUND_START, AFTER_DRAW, SHUFFLE,
	CARD_PLAYED, CARD_DISCARDED, UNIT_DEPLOYED, UNIT_DIED, UNIT_KILL,
	UNIT_HIT, UNIT_HURT, UNIT_HEALED, DOT_TICK, COUNTER, ROUND_END, ROUND_SETTLED,
	BATTLE_WON, POTION_USED, SHOP_OPEN, RELIC_GAINED
}
enum Rarity { COMMON, RARE, BOSS }

@export var rarity: Rarity = Rarity.COMMON
## 流派标签，用于掉落加权与图鉴分组：wide / tall / death / dot / control / cycle / guard / ranged / economy / neutral
@export var tags: Array[StringName] = []
@export var trigger: Trigger = Trigger.NONE
## 复杂效果的处理函数名，注册在 RelicRuntime；简单数值效果留空走通用处理器
@export var handler: StringName = &""
```

> **关键陷阱**：`kind` 的默认值是 `DRAW_ENERGY`，而旧遗物 `draw_engine.tres` 正是靠「不写 kind」拿到这个默认值。所以**不能改默认值**，只能追加 `Kind.NONE = 5`，并要求每件新遗物显式写 `kind = 5`。否则 60 件新遗物会全部被 `record_draws()` 当成抽牌引擎，每 10 抽白送能量。
>
> 建议在 `add_relic()` 或编辑器校验里加一条警告：`trigger != NONE and kind == DRAW_ENERGY and handler == &""` 时提示「新遗物缺少 Kind.NONE」。

旧字段 `kind`、`amount`、`draw_threshold`、`rounds` 全部保留，旧 `.tres` 不受影响。`add_relic` 里的 `BASE_DEFENCE` 过滤也要保留。

### 3.5 信号挂钩表

不用新造事件总线，现有信号够用：

| 触发点 | 现成入口 | 注意 |
| --- | --- | --- |
| 战斗开始 | `BattleRoundManager.start_encounter()` | 早于首轮抽牌 |
| 每轮开始 | `BattleRoundManager.phase_changed(CARD_PLAY, round)` | 抽牌在信号之后，`ROUND_START` 要抢在抽牌前 |
| 回合结算 | `BattleRoundManager.round_settled(result, damage, ...)` | 已带胜负与伤害拆分 |
| 抽牌 | `HandManager.draw_cards()` → `RunManager.record_draws()` | 只有真正抽入手牌才计数 |
| 洗牌 | `HandManager.draw_cards()` 的补牌分支 | 建议在洗牌处加一个 `shuffled` 信号 |
| 出牌 | `CardBattleRuntime.try_play()` | 区分征召 / 效果 / 消耗 |
| 部署 | `CardBattleRuntime._spawn_prepared()` | 只算征召牌，镜像/策反不算 |
| 死亡 | `UnitBase.unit_died` | 清场不触发；payload 带阵营 |
| 击杀 | `UnitBase.kill_confirmed` | 带 killer，可直接归因 |
| 受击 | `UnitBase.hit_received` / `get_hurt()` | `damage_kind` 区分普攻 / 技能 / 毒 |
| 反击 | `UnitBase.get_hurt()` 的反击分支 | 建议加一个 `countered` 回调 |
| 持续伤害 | `CardBattleRuntime._on_round_ended()`（毒）/ 流血计时 | 毒在回合末，流血按秒 |
| 治疗 | `UnitBase.receive_healing()` | 可拿到溢出量 |
| 护盾 | `UnitBase.add_shield()` / `clear_shield()` | 「破盾」需要新增一个信号 |
| 战斗胜利 | `BattleScene.finish_battle(true)` | 在发奖之前 |
| 药水 | 药水运行器首次有效落点 | 无效落点不算 |
| 商店 | `scripts/shop/shop_session.gd` | 价格计算入口 |
| 金币 | `RunManager.gold` 的 setter | 增减都会触发 |

**不要**用 `_process` 每帧扫描全场。60 件遗物 × 每帧 × 几十个单位，会直接把战斗拖慢。

### 4.1 军团铺场（wide）

**定位**：用数量和兵种多样性赢；怕单体质量、怕清场后加费。
**现有支撑**：合理搭配、战友、镜像、不灭军势、低费征召。

| 遗物 | 稀有度 | 触发 | 效果 | 联动 |
| --- | --- | --- | --- | --- |
| 军团旗幡 `war_banner` | 普 | `ROUND_START` | 手牌中征召牌 ≥2 时，本回合第一张征召牌费用 −1（最低 0），每轮 1 次 | 铺场启动、战友 |

## 5. 组合与成型路线

### 5.1 亡灵军团（铺场 + 亡语）

**目标遗物**：军团旗幡 → 骨灰之瓮 → 征兵名册 → 送葬人 → 死亡回响 → 大地祭坛 / 不朽王座。

**打法**：
1. 每轮先铺 2 个低费单位，保证场上 ≥4。
2. 主动让残血单位送死：骨灰之瓮打真伤，送葬人补手牌，殉道冠喂大哥。
3. 后期大地祭坛每轮额外削 4 点敌方 HP，用人数差赢。

**关键决策**：什么时候停止铺场、把哪个单位喂给传承 / 殉道；手里永远留 1 张征召牌防清场。

### 5.2 独狼剑圣（单核）

**目标遗物**：淬火铁砧 → 决斗契约 → 独狼徽记 → 传承之证 → 王者之剑。

**打法**：
1. 第 1 轮只下 1 个骑士 / 剑士。
2. 力量强化、护甲加固全堆它；第一个强化吃铁砧 +50%。
3. 队友死了给传承；击杀触发王剑回能，继续堆。

**关键决策**：是否为了独狼放弃铺场；什么时候补第二个单位防麻痹。

### 5.3 毒火炼金（DOT + 药水）

**目标遗物**：腐蚀之瓶 → 余烬之核 → 硫磺之心 → 疫医面具 → 焚城之焰 / 炼金行囊。

**打法**：
1. 前期靠普攻附毒磨血。
2. 第 2 轮开始用烈焰灼烧 / 火焰药水覆盖；余烬之核让火区更疼。
3. 毒层数转攻击增伤；首杀滚出火区。

**关键决策**：毒和火的覆盖顺序；药水留给精英波次还是 Boss。

## 6. 获取、稀有度与经济

### 6.1 稀有度分布

| 稀有度 | 数量 | 建议价格 | 掉落来源 |
| --- | --- | --- | --- |
| 普通 | 27 | 140–160 | 普通战斗、商店、宝箱 |

| 首领 | 9 | 不出售 | Boss 必掉、首领事件 |

### 6.2 掉率调整

| 来源 | 当前 | 建议 | 理由 |
| --- | --- | --- | --- |
| 普通战斗 | 5% | 12% | 15 场战斗期望 1.8 件，能开始凑套 |
| Boss | 10% | 100%（首领池三选一） | 每幕一个明确的 build 节点 |
| 宝箱 | 固定 1 件 | 保持，改三选一 | 玩家的第一次定向选择 |
| 商店 | 3 格 | 保持，至少 1 稀有 | 金币有去处 |
| 事件 | 随机 | 保持 | 惊喜位 |

**一局预期**：15 场战斗 × 12% ≈ 1.8 + 3 Boss + 3 宝箱 + 1–2 商店 ≈ **8–10 件**。这正好够 1 个主流派 + 1 个副流派。

### 6.3 智能掉落（可选，但强烈建议）

60 件池子里随机抽，玩家容易拿到互斥件（铺场 + 独狼）。建议掉落时按 `tags` 加权：

- 已持有流派标签：权重 ×1.5。
- 完全未持有的流派：保底权重 ×0.8，避免永远见不到。
- 互斥标签：权重 ×0.3（铺场 ↔ 单核，亡语 ↔ 防守）。
- 首个遗物 / 第一个宝箱：**必出三选一**，让玩家主动定方向。

### 6.4 图鉴与可见性

- 图鉴按 `tags` 分页，显示「已收集 / 总数」，给长线目标。
- 未获得的遗物只显示轮廓与流派，不剧透具体数值。

**运行时骨架**：

```gdscript
# scripts/battle/relic_runtime.gd
extends Node
class_name RelicRuntime

var battle: Node
var _counters: Dictionary = {}   # id -> {battle:int, round:int, last_time:float}
var _handlers: Dictionary = {}   # StringName -> Callable

func _ready() -> void:
	battle = get_parent()
	_register_handlers()
	var rounds: BattleRoundManager = battle.get_node("BattleRoundManager")
	rounds.phase_changed.connect(_on_phase_changed)
	rounds.round_settled.connect(_on_round_settled)

func fire(trigger: int, payload: Dictionary = {}) -> void:
	for relic in RunManager.relics:
		if relic.trigger != trigger:
			continue
		if not _can_fire(relic):
			continue
		var handler: Callable = _handlers.get(relic.handler, Callable())
		if handler.is_valid():
			handler.call(relic, payload)
			_mark_fired(relic)
			SignalBus.relic_triggered.emit(relic.id, relic.display_name)

func _can_fire(relic: RelicDefinition) -> bool:
	var c: Dictionary = _counters.get(relic.id, {})
	if relic.max_per_battle > 0 and int(c.get("battle", 0)) >= relic.max_per_battle:
		return false
	if relic.max_per_round > 0 and int(c.get("round", 0)) >= relic.max_per_round:
		return false
	return true
```

> 复杂效果走 `_handlers`（复活、复制伤害、商店折扣、药水增幅）；简单数值走通用处理器读 `amount` / `rounds`。不要为每件遗物写一个脚本。

**两个容易踩的坑**：

1. `RunManager.add_relic()` 会 `duplicate(true)` 后再存进本局。任何「运行期计数」都不能写在 `RelicDefinition` 上——每个副本各算各的，读档还会重置。计数统一放 `RelicRuntime`；跨战斗的放 `RunManager` 并加进 `SAVE_KEYS`。
2. 「三选一」不是改个数字：`battle_reward_session.initialize()` 现在只生成 1 件遗物 offer，要改成 3 件候选，并复用卡牌三选一的 UI 与 `claim(index, card_index)` 流程。

### 7.3 UI 与可读性

- **触发提示**：HUD 右侧飘一条「遗物名 · 效果」，同帧合并，最多 1 条 / 0.25 秒。
- **战斗跳字**：遗物伤害用青色 `#7ad7ff`，与技能金色、毒紫色区分。
- **悬停说明**：显示「本场已触发 2/3」这类进度，和十抽引擎保持一致。
- **图标**：现有 `assets/ui_redrawn/icons/` 只有 8 个通用图标，60 件需要扩充；P0 阶段按流派复用占位（每个流派 1 个），正式美术按 10 个流派 × 6 个规划。

### 7.4 测试与回归

新增 `--relics-regression`，覆盖：

1. 每件遗物的触发次数与上限（每回合 / 每场 / 冷却）。
2. 存档往返：长期计数不丢、每场计数正确重置。
3. 重复获取同 ID 不叠加（沿用 `add_relic`）。
4. 战斗结束、主动退出、切幕时计数清零，不污染下一场。
5. 暂停与战斗倍速不影响触发次数与计时。
6. 随机类遗物（命运硬币、恐惧图腾）使用战斗 RNG，固定种子可复现。
7. 遗物伤害不触发反击、不触发吸血（走 `take_effect_damage`）。

**验收标准**：

- 连跑 3 局，每局都能说出「这局我在玩什么流派」，且 3 局的主流派不全相同。
- 一局遗物 6–10 件，其中同流派至少 3 件。
- 单场战斗因遗物触发增加的时长 < 2 秒，HUD 提示不刷屏。
- 除明确设计为高频的遗物外，单件单局触发不超过 30 次。

## 8. 风险与反模式

### 8.1 五条红线

1. **无限循环**：抽牌→能量→抽牌；死亡→回手→死亡；治疗→护盾→治疗。全部加上限。
2. **隐形收益**：自动战斗里看不见的触发等于没有，必须 HUD 提示。
3. **乘算爆炸**：同类百分比加成走加法池，同一属性合计上限 +60%；单件可以给高值（如铁砧 +50%），但多件不连乘。
4. **顺序依赖**：同一时机固定结算顺序（见 3.2），不能靠节点顺序碰运气。
5. **每帧扫描**：只用信号；确需计时的用 `Timer`，不用 `_process`。

### 8.2 不要做的遗物

| 反模式 | 为什么不行 | 改法 |
| --- | --- | --- |
| 「全体攻击 +1」无触发 | 纯数值，没有决策 | 改成「部署第 3 名时 +2，持续本场」 |
| 「每回合 +1 能量」无上限 | 直接超过储能水晶 | 改成「手牌 ≥3 时下回合 +1，每场 3 次」 |
| 「死亡后立即复活」无限次 | 配合亡语直接无敌 | 每场 1 次，且复活不触发死亡遗物 |
| 「商店价格 −100%」 | 经济系统崩坏 | 上限 −30% |
| 「每次受击反弹全部伤害」 | 人海反伤失控 | 固定 3 点真伤 + 每敌每秒 1 次 |
| 需要玩家实时操作的遗物 | 自动交锋阶段无法微操 | 改成开局 / 出牌 / 回合末触发 |

### 8.3 调参顺序

先调**触发次数上限**，再调**数值**，最后调**掉率**。反过来会先被掉率掩盖问题，再被数值打崩。
