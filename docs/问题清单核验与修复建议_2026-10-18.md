## 关键探针证据

### 单位初始化

在不改正式源码的探针中，真实 soldier.tscn 的时序是：

```text
new UnitBase: health=null
child_entered_tree: ready=false, health=null
add_child 返回后: ready=true, health=100
```

正常 add_child 调用会在同一调用链内完成 ready；所以早登记本身不必然跨帧泄漏 null。不过登记回调会同步调用其他系统，ready 也可能因错误中断，当前没有完整失败围栏。`tactical_effect_runtime._alive()` 把未初始化生命视作活单位，统一存活方法前必须明确这一语义。

建议把生命初始化与有效性建立在登记之前，或在 ready 后完成登记；同一入口统一判定战场归属、有效数据、初始化完成、死亡和待删除。无 unit_data 的单位不仅要拒绝登记，也要在创建/入树入口阻止后续子节点继续解引用。

### 物理倍速

关闭 BattleSpeed 的自动覆盖后，分别设置与正式 `_apply()` 相同的引擎参数，按真实单调时钟采样 1.5 秒：

```text
1×：90 步 / 1.499953 秒 = 60.00 步/秒
3×：271 步 / 1.509632 秒 = 179.51 步/秒
```

物理频率决定真实时间内的步数，time_scale 缩放传入的游戏 delta。二者同时设为 3 倍保持单步游戏 delta 约 1/60，实际计算频率约 3 倍；没有再相乘到 540 步。改变这一策略前应保留原有胜负与事件一致性回归。

### Global 无脚本的可重复触发方式

额外对照探针使用同一项目、同一 Godot 版本，只改变领域类型被解析的入口：

```text
SceneTree 主脚本声明 var probe_card: CardInstance：
  UnitBase / Global 编译报 Identifier not found: SignalBus
  Global: script_attached=false, can_instantiate=false

SceneTree 延迟 load 一个 Node 脚本，再在该 Node 声明相同类型：
  Global: script_attached=true, can_instantiate=true
  is_card_play_phase 方法存在，无业务脚本错误
```

这证明提前解析领域类型会牵入 UnitData、SkillBase、UnitBase、Global 等启动依赖，早于 autoload 标识可用的时机。`game_session_smoke.gd` 虽然 `_run.call_deferred()`，整份脚本的类型仍在此前解析，其中有 CardInstance 类型的 lambda。SignalBus 的信号类型引用 Global.GamePhase，而 Global 的 setter 又直接引用 SignalBus，进一步扩大了启动耦合。

**建议的第一步是统一测试启动壳：SceneTree 入口保持不依赖领域类型，autoload 完成后再 load 实际 Node 测试。** 现有 card_framework_test_runner 已使用这种方式。随后再把纯类型/枚举与运行服务分离，并增加不依赖 Global 自身的全入口启动检查。只把函数 call_deferred 或调换两个 autoload 顺序，不足以消除早期类型解析问题。

这是本轮新建立的可重复触发条件，不能据此断言 10-17 那份历史巨型日志只有这一种成因；正常延迟入口中 Global 初始化有效，未证明玩家常规主场景启动必然失败。
