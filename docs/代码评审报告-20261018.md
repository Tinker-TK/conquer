### 0.2 最值得保留的五个做法

1. **战斗规则单一真相源**：玩家 HP 只在 `RunManager`，Round/能量/敌 HP 只在 `BattleRoundManager`，战斗侧只读。
2. **异步表现与规则解耦**：牌堆先改真实状态，再发动画请求；扣血动画用 generation 阻断结束后的旧回调。
3. **Godot 共享资源纪律**：单位 `unit_data`、SpriteFrames、材质、卡效果、卡费用全部按实例复制，注释写明“为什么”。
4. **验证先于扣费**：出牌先验证目标/费用/全部效果，失败不吞牌不扣能量；错误信息直接面向玩家。
5. **写回安全链**：配置工具“校验→备份→sha256→引擎回读→回滚→原子替换”，在地图/波次编辑器里做得相当完整。

### 0.3 最需要先处理的五个问题

1. **许可风险（发布阻断级）**：Eslabong 特效库的 EULA 明确 personal / non-commercial、禁止反编译与衍生，而库正是从本机 PCK 恢复并已接入战斗。
2. **运行时错误没有围栏**：`Global` autoload 异常时，多个每帧调用点持续报错，单个会话写出 **22.1 GB** `godot.log`。
3. **数值类型缺失**：`current_health` 是无类型 Variant，`living_units()` 直接 `> 0` 比较；单位 `_ready` 失败一次，之后每帧报 `Nil > int`。
4. **版本控制与仓库卫生**：SVN 里版本化了 `.godot`（3,359 节点）和 `.maintenance`（5,826 节点 / 550 个顶层条目），`.gitignore` 对 SVN 无效，工作副本 25.9 GB。
5. **正式路线文件缺失**：运行时只读 `data/run/game_map*.json`，三幕文件都不存在，游戏会回落到 `map.gd` 里写死的十层测试图；作者路线 JSON 只被测试引用。

## 2. 做得好的地方

### 2.1 战斗规则收敛，状态机与异步收尾都很克制

`BattleRoundManager` 把 Round、阶段、能量、敌我 HP、回合伤害都收在一个类里（[battle_round_manager.gd](../scripts/battle/battle_round_manager.gd)）；状态机 `PREPARING → PLAYER_PHASE → COMBAT → ROUND_END → DAMAGE_SETTLEMENT → NEXT_ROUND/VICTORY/DEFEAT` 明确，非法转移直接 return。更关键的是两处“防串场”设计：

- `request_round_check()` + `call_deferred()` 把同帧多次死亡合并为一次检查（[:129-141](../scripts/battle/battle_round_manager.gd#L129-L141)）；
- `_settlement_generation` 在每轮结算/结束时自增，扣血回调、动画完成、清场前都校验 generation（[:170-200](../scripts/battle/battle_round_manager.gd#L170-L200)），彻底避免“上一轮的伤害打到下一轮单位”。

这两点是整个项目里最像“上线过”的代码。

### 2.2 表现与规则解耦，界面动画不拖慢结算

`HandManager` 的注释就是设计原则：“界面收到的是移动说明，不是修改牌堆的命令；动画完成与否不影响游戏规则”（[hand_manager.gd:24-26](../scripts/cards/hand_manager.gd#L24-L26)）。抽牌/出牌/弃牌都是先更新真实牌堆，再 `card_motion_requested`；`begin_resolve` 先移出原牌再触发随机连锁，避免“抽到自己”（[:120-137](../scripts/cards/hand_manager.gd#L120-L137)）。同类思路还体现在：

- 回合扣血：`play_round_damage()` 等光弹和余辉全部播完才清场（[battle_scene.gd:246-256](../scripts/battle/battle_scene.gd#L246-L256)）；
- 手牌离场：先 reparent 到动画层再清状态，用 WeakRef 跟随目标（[hand_presenter.gd:348-377](../scripts/ui/hand_presenter.gd#L348-L377)）。

### 2.3 对 Godot 共享资源的“坑”有系统性防御

这是很多 Godot 项目会翻车、而本项目做得对的地方：

- 单位进场 `unit_data = unit_data.duplicate()`，SpriteFrames 与材质也各复制一份（[unit_base.gd:99-122](../scripts/units/unit_base.gd#L99-L122)），注释写明“避免一个单位修改资源时影响整队”；
- 卡牌强化先 `definition.duplicate(true)` 再改效果（[card_instance.gd:157-166](../scripts/cards/card_instance.gd#L157-L166)）；
- 每条效果施加时做快照 `effect.duplicate()`（[card_battle_runtime.gd:575-585](../scripts/cards/card_battle_runtime.gd#L575-L585)）；
- 世界天气运行时复制 settings，避免污染预设（[rain_weather.gd](../scripts/world/rain_weather.gd)）。

### 2.4 出牌验证严格，失败不吞资源

`try_play()` 在扣费/生成单位之前完成目标选择、全部效果验证、单位场景预检（[card_battle_runtime.gd:230-302](../scripts/cards/card_battle_runtime.gd#L230-L302)）；失败时把已预检的单位 `free()` 掉，不扣能量、不弃牌。验证信息是面向玩家的中文原因（“请放在已烘焙导航的左半边可行走区域…”），并且对“收回必须是最后一步”“随机出牌必须在最后”“生命不能降到零”等组合规则有专门检查（[:366-410](../scripts/cards/card_battle_runtime.gd#L366-L410)）。这套细节显著降低了卡牌系统的“看似能出、实际空放”问题。

### 2.5 数据驱动 + 策划友好，且认真做了兼容

- 16 个 `@tool` Resource，307 个 `@export`，116 个带 `@export_range`，几乎逐字段写清“改这个不会改变什么”（如 [unit_data.gd](../data/units/unit_data.gd)、[card_effect.gd](../data/card_effects/card_effect.gd)）；
- 枚举坚持“只追加、保留旧编号”，删除的效果显式留空位（[card_effect.gd:8-19](../data/card_effects/card_effect.gd#L8-L19)）；
- 旧字段用 `_set()` 迁移（[skill_base.gd:148-155](../data/skills/skill_base.gd#L148-L155)）；存档版本 1→2 的迁移写在 `RunManager.load_saved_run()` 里；
- 战术/卡牌效果的验证消息直接是玩家可读的中文，不是“invalid config”。

### 2.6 配置写回链路是“工程化”的亮点

`tools/config_catalog/catalog.py` 的保存流程值得保留：校验 → 备份 → 逐文件 sha256 复核 → 引擎回读 → 异常回滚，并挡路径越界；地图/波次编辑器用了同目录 staging、保留 UID、写前写后指纹、`tmp + rename`、保存前 sha256 冲突检测（详见 [map_editor/document.gd](../addons/map_editor/document.gd)、[wave_editor/document.gd](../addons/wave_editor/document.gd)）。这类“写配置前先自证”的投入，在编辑器工具里算很高的标准。

### 2.7 测试体系的规模与“真实度”都超出同类项目

- 123 个测试脚本 / 21,661 行，统一入口 [card_framework_test_runner.gd](../tests/card_framework_test_runner.gd) + [run_checks.py](../tools/maintenance/run_checks.py)；
- 不只测纯函数：实例化正式 `battle_scene`、走真实拖放与平滑输入、用 `AudioEffectCapture` 验证真实混音、渲染真实像素；
- 失败判据四重：退出码 + 完成标记 + 日志 `ERROR:` 扫描 + 断言；每项独立 Godot 进程、独立 user 目录、60 秒超时；
- 有确定性意识：固定种子验证“特效/飘字不消耗全局 RNG”，倍速测试逐事件对比结果；
- 有跨进程持久化：三幕测试真的再起一个 Godot 验证存档；
- 有全量扫描：505 套技能、839 个资源、3,108 条路径。

### 2.8 世界表现层与场景组合有明确积累

四层导航每层只烘焙一次并释放 RID（[battle_floor_map.gd](../scripts/world/battle_floor_map.gd)）；雨天用独立 SubViewport 做倒影/水波/折射，雪天做逐层遮罩与堆积；关卡用继承（`battle_001.tscn` 继承 `battle_scene.tscn`），地图把 EventPanel/ShopPanel 作为子场景组合，160 个场景有 77 处 `instance`。

### 2.9 特效层有统一门面与缩放体系

`combat_vfx.gd` 把“战斗只调用视觉接口、伤害始终由单位系统结算”写成了静态门面（[combat_vfx.gd](../scripts/effects/combat_vfx.gd)）；Eslabong 的 432 条缩放 profile（430 条实测）按 18px 身体高度做基准，引用完整性经全量核对为零悬空；第三方库（MIT/CC0）与恢复库在目录上分开，许可文件保留。

### 3.1 P0

#### P0-1 特效库许可风险（发布阻断）

- 证据：[SOURCE_LICENSE.txt:5-10](../assets/effect/eslabong_vfx/SOURCE_LICENSE.txt#L5-L10) 明确授予的是“personal, non-exclusive, non-transferable ... private, non-commercial entertainment purposes”，并禁止 decompile/reverse engineer、禁止 modify/derivative works、禁止 redistribute。
- 但 [README.md:38](../assets/effect/eslabong_vfx/README.md#L38) 写明“来源是本机安装的 Eslabong Demo ... 读取原安装目录，在本项目中恢复资源”，恢复了 355 个场景 / 224 张贴图；`.maintenance/eslabong/` 还留有 `decrypted.pck`、GDRE 工具与 `recovered/` 工程。
- 该库已接入实战：游戏侧有 26 处 Eslabong 引用（效果名与 `Skills.find(...)` 配方），多个 `scripts/combat/*` 直接 `extends` 库的 `skill_player.gd`。
- 影响：若计划商业发行或公开仓库，这是直接的法律风险，不是代码问题；仅“把许可文件放进去”不构成授权。
- 建议：法务立即确认；发布前替换为自制/已授权素材。研究用途也应把恢复产物移出 `assets/`（放到不参与导出的目录），并从默认导出排除。
- 同类待确认：`pixel_vfx/licenses/craftpix_magic.txt` 只有一行 URL，未存许可原文；Alenia/Craftpix 对“原始素材再分发”通常有限制。

#### P0-2 每帧错误没有围栏，单个日志膨胀到 22.1 GB

- 证据：`.maintenance/card-effect-name-qa/preview-userdata/Godot/app_userdata/ballsprite/logs/godot.log` 为 **22,139 MB**；尾部持续输出：
  - `Invalid access to property or key 'game_phase' on a base object of type 'Node'`，调用点包括 [card_battle_runtime.gd](../scripts/cards/card_battle_runtime.gd)、[battle_camera.gd:150](../scripts/battle/battle_camera.gd#L150)、[battle_items.gd:54](../scripts/items/battle_items.gd#L54)、[battle_speed.gd:44](../autoload/battle_speed.gd#L44)、[team_a_base.gd:31](../scripts/units/team_a_base.gd#L31)、[hand_presenter.gd:290](../scripts/ui/hand_presenter.gd#L290)；
  - `Invalid operands 'Nil' and 'int' in operator '>' at living_units (card_battle_runtime.gd:159)`。
- 说明：该次运行中 `Global` 退化成了一个没有脚本的普通 Node（原因未复现），而代码对 `Global.game_phase` 是每帧直接访问、无任何守卫；Godot 文件日志默认开启，于是错误以每帧多条的速率写盘。
- 影响：磁盘被打满、日志无法诊断、真实错误被淹没；这也解释了为什么 `.maintenance` 会长到 25.9 GB。
- 建议：
  1. 给阶段访问加单一入口（静态 `GamePhaseService`）或启动自检：`Global` 脚本缺失时立即 `push_error` 并 `quit`，而不是每帧报错；
  2. 在 `run_checks.py` / 开发启动器里加日志大小上限与会话时长上限（例如 > 200 MB 直接 kill 并判失败）；
  3. 对高频错误做一次性标记（`push_once` 风格），避免同一错误刷屏。

#### P0-3 `current_health` 无类型，注册顺序可触发每帧崩溃

- 证据：[unit_base.gd:86](../scripts/units/unit_base.gd#L86) `var current_health` 无类型、无初值，只在 `_ready()` 里赋值；而 [card_battle_runtime.gd:161](../scripts/cards/card_battle_runtime.gd#L161) 的 `living_units()` 直接 `unit.current_health > 0`，没有 null 检查。
- 旁证：[tactical_effect_runtime.gd:25](../scripts/cards/tactical_effect_runtime.gd#L25) 已经写成 `(unit.current_health == null or unit.current_health > 0)`——说明开发者踩过“单位还没 `_ready` 就被登记”的坑，但只修了一个调用点。日志中的 `Nil > int` 正是同一问题的另一处。

- 3× 倍速不是放大 delta，而是把物理频率提到 180 Hz（[battle_speed.gd:51-56](../autoload/battle_speed.gd#L51-L56)）；配合 `time_scale=3`，真实物理步数约 9 倍（每秒约 540 步 vs 60 步），没有降级策略；
- UI 侧 5 个每帧脚本（手牌悬停、详情 10 Hz、药水 HUD 每帧写文本、书本 `UPDATE_ALWAYS`、植被每物理帧写 modulate）。

建议：静态阶段 `set_physics_process(false)`；索敌结果按“目标存活 + 视线/距离变化”失效而非固定 20 帧；穿透弹用物理查询/空间哈希；倍速提供“粗步长”模式；UI 全部改事件驱动。

#### P2-2 场景与资源体积

`battle_scene.tscn` 160 KB / 3,082 行，含 44 个手摆 Clouds 精灵、14 个 TileMapLayer；`assets` 274.5 MB（`pixel_vfx` 47 MB 仅 1 处运行引用，其中 37.7 MB 是原始 ZIP；`eslabong` 20.2 MB 静态只引用少量效果）；`docs/game_config_catalog.html` 1.1 MB 生成物入库。`outputs/` 300 MB 既未进 `.gitignore`，也未进 `export_presets.cfg` 的 `exclude_filter`，按 `export_filter="all_resources"` 有随包发布风险（PCK 实际体积待实测）。建议：云层改 GPU 粒子/合批，`source/` 与原始 ZIP 移出 `assets`，生成物与截图不进版本库，导出显式排除 `outputs/*`。

#### P2-3 VFX 数据“三份”

`skill_catalog.json` 903,709 B、`skill_catalog_data.gd` 903,744 B、`SKILL_COMBINATIONS.md` 67.8 KB 内容重复；`catalog.json` 与 `catalog_data.gd`、`scale_profiles.json` 与 `scale_profiles_data.gd` 同样成对。GD 是导出安全镜像（`catalog_data.gd` 有生成头，技能数据没有），但两份都入库、都在改。建议：单一 JSON 源 + 构建期生成 GD（或直接把 JSON 放进导出过滤），生成文件加“DO NOT EDIT”与 CI 校验。

#### P2-4 调试用 MCP 服务体量过大

`autoload/mcp_interaction_server.gd` 4,392 行，是最大单文件；虽然 `_ready()` 用 `OS.is_debug_build()` 挡住了 release 启动，但代码仍随包编译，且含 `eval` 任意脚本执行。建议移到 `addons/` 或独立调试工具，用 feature tag 条件编译/加载。

#### P2-5 文档与实现漂移

- `README.md` 与 `.maintenance/README.md` 声称 `.maintenance` 只保留备份与当前结果、其余归档到项目外；实际 58,428 文件 / 25.9 GB。
- `tests/README.md:77` 声称 headless 跳过的 GPU 检查不算通过，实际 `rain_floors`/`snow_floors` 仍以 marker 通过。
- `docs/项目清理记录.md` 的 47 项 / 1,601 路径 / 21 场景与当前 107 默认检查 / 3,108 路径 / 44 场景不一致。
建议：把“当前事实”收敛到单一 manifest，由脚本生成 README 的检查表与统计；文档里避免手写数量。

#### P2-6 命名与拼写债务

`BisicUI`、`GlodCoin`、`Charpter`、`MouseSlectionController`、`Dectrition`/`Decrition`、`card_discription` 等 93 处已进入节点路径/字段名，纠正即破坏兼容。建议一次性重命名 + `%UniqueName` + 兼容别名，之后用命名规范/CI 拼写检查兜住新增。

#### P2-7 可访问性与输入方式

奖励/商店/药水按钮大量 `FOCUS_NONE`，模态打开不 `grab_focus`；详情面板仍有 11–13 px 字号；中文字体回退列表在 5 个脚本/主题里各维护一份，自绘文本依赖隐式回退。建议：统一 Theme/FontVariation，最小字号 18–20，模态焦点链，UI 缩放选项。

#### P2-8 缺少本地化与文本集中管理

中文文案散落在脚本、资源、场景、测试断言中（测试甚至断言精确文案）；没有 i18n 表。若未来出海，这是大工程。建议至少把玩家可见文案收到 `data/text/` 或以 `tr()` 包裹。
